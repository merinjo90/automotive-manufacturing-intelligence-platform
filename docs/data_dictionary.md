# Data Dictionary — Automotive Manufacturing Intelligence Lakehouse

This document describes all four synthetic datasets generated by this
project. All data is synthetic, created solely for learning and portfolio
demonstration. It does not contain real data from any automotive
manufacturer, supplier, SAP, MES, ERP, or production system.

---

## 1. supplier_deliveries

**Business meaning:** One row represents a single shipment event — a
supplier delivering a specific component to a specific plant against a
purchase order.

**Generator:** `src/generators/supplier_deliveries.py` →
`generate_supplier_deliveries(num_records)`

| Field | Type | Description |
|---|---|---|
| delivery_id | string | Unique identifier for this delivery |
| supplier_id | string | Which supplier made this delivery |
| component_id | string | Which component was delivered |
| plant_id | string | Which plant received the delivery |
| purchase_order_id | string | The purchase order this delivery fulfills |
| planned_delivery_date | date | When the delivery was scheduled |
| actual_delivery_date | date | When the delivery actually arrived |
| ordered_quantity | integer | Units ordered |
| delivered_quantity | integer | Units actually delivered |
| accepted_quantity | integer | Units passing incoming inspection |
| rejected_quantity | integer | Units failing incoming inspection |
| delivery_status | string | Normally "LATE" in this sample |

**Known invalid-data categories (≈5% of records):**
- Missing `delivery_id` (empty string)
- Invalid `delivery_status` ("UNKNOWN_STATUS")
- Impossible quantity relationship (`accepted_quantity + rejected_quantity != delivered_quantity`)

## 2. production_orders

**Business meaning:** One row represents a single production order — an
instruction to build a specific quantity of a vehicle model on a specific
production line, with planned and actual outcomes tracked.

**Generator:** `src/generators/production_orders.py` →
`generate_production_orders(num_records)`

**Known limitation:** `_time` fields currently store date-only precision
(no hour/minute). Full timestamp support is a planned future improvement,
documented as an intentional scope decision for this version.

| Field | Type | Description |
|---|---|---|
| production_order_id | string | Unique identifier for this order |
| vehicle_model_id | string | Which vehicle model is being built |
| plant_id | string | Which plant is producing this order |
| production_line_id | string | Which line is producing this order |
| planned_start_time | date | Planned start (date-only precision) |
| actual_start_time | date | Actual start (date-only precision) |
| planned_end_time | date | Planned completion (date-only precision) |
| actual_end_time | date | Actual completion (date-only precision) |
| planned_quantity | integer | Units planned to be produced |
| actual_quantity | integer | Units actually produced |
| rework_quantity | integer | Units requiring rework |
| scrap_quantity | integer | Units scrapped |
| production_status | string | Normally "COMPLETED" in this sample |

**Known invalid-data categories (≈5% of records):**
- Missing `production_order_id` (empty string)
- Invalid `production_status` ("UNKNOWN_STATUS")
- Negative `scrap_quantity`

**Guaranteed invariant (tested):** `actual_end_time` is never before
`actual_start_time`.

## 3. quality_inspections

**Business meaning:** One row represents a single inspection event on a
vehicle or component, recording whether it passed or failed, and if
failed, the defect details.

**Generator:** `src/generators/quality_inspections.py` →
`generate_quality_inspections(num_records)`

| Field | Type | Description |
|---|---|---|
| inspection_id | string | Unique identifier for this inspection |
| vehicle_id | string | Which vehicle was inspected |
| component_id | string | Which component was inspected |
| supplier_id | string | Which supplier's component this is |
| plant_id | string | Which plant performed the inspection |
| production_line_id | string | Which line the item came from |
| inspection_timestamp | date | When the inspection occurred |
| inspection_result | string | "PASS" or "FAIL" |
| defect_code | string | Type of defect (empty if PASS) |
| defect_severity | string | Severity of defect (empty if PASS) |
| rework_required | boolean | Whether rework is needed |
| scrap_required | boolean | Whether scrap is required |

**Known invalid-data categories (≈5% of records):**
- Missing `inspection_id` (empty string)
- Invalid `defect_severity` ("EXTREME")
- Orphaned `component_id` ("COMP999" — references a component not in
  the known component list, simulating a referential-integrity failure)

**Guaranteed invariant (tested):** every `PASS` record has an empty
`defect_code` and `rework_required = False`.

## 4. machine_downtime

**Business meaning:** One row represents a single machine downtime
event — either scheduled maintenance or an unplanned breakdown — and
its impact on production.

**Generator:** `src/generators/machine_downtime.py` →
`generate_machine_downtime(num_records)`

| Field | Type | Description |
|---|---|---|
| downtime_event_id | string | Unique identifier for this event |
| machine_id | string | Which machine was affected |
| production_line_id | string | Which line the machine is on |
| start_timestamp | date | When downtime started |
| end_timestamp |

date | When downtime ended |
| downtime_reason | string | Reason for downtime |
| planned_flag | boolean | True if scheduled maintenance |
| production_loss_units | integer | Units of production lost |

**Known invalid-data categories (≈5% of records):**
- Missing `downtime_event_id` (empty string)
- Negative `production_loss_units`
- `end_timestamp` before `start_timestamp` (a genuine timestamp
  inversion, guaranteed by construction using a forced minimum 1-day
  offset)

## Shared design patterns across all four generators

- Every generator uses the same three shared helpers from `src/common/`:
  `should_create_invalid_record()`, `generate_random_date()`, and
  `write_records_to_csv()`.
- Exactly one `should_create_invalid_record(0.05)` check per record
  controls whether it becomes invalid at all (~5% of records). If
  invalid, exactly one corruption type is selected at random via
  `random.choice()` on a list of corruption functions, ensuring every
  invalid record has one clear, traceable reason.
- Each dataset has its own formal Pytest test suite in `tests/unit/`,
  covering: correct record count, complete field presence, invalid-rate
  range, and at least one dataset-specific structural or business-rule
  check.
